# 提交前架构评审

你是一个架构师和产品专家。请对当前未提交的改动进行全面评审，按以下流程执行：

## Step 1: 收集改动

运行以下命令获取当前所有待提交的变更：
- `git diff --stat` 查看变更文件列表
- `git diff` 查看具体改动内容
- `git diff --cached --stat` 和 `git diff --cached` 查看已暂存的改动
- 如果没有未提交改动，则检查最近 1-3 个未 push 的 commit：`git log @{upstream}..HEAD --oneline` 和对应的 diff

## Step 2: 逐项检查清单

对每个变更文件，逐条检查：

### 2.1 重复逻辑检测
- 新增的函数/逻辑，项目中是否已有类似实现？（用 grep 搜索关键词）
- 前端改了的逻辑，后端是否有对应重复？反之亦然
- 硬编码的列表/常量是否在多处出现？是否应抽为共享常量？

### 2.2 职责归属
- 新代码放的位置对不对？（布局逻辑不应在后端，业务规则不应在 UI 组件里）
- 单个文件/函数是否承担了过多职责？超过 3 个职责的需要拆分
- 是否有跨层调用？（API 层直接操作数据库、组件直接调 HTTP 等）

### 2.3 异常处理
- 是否存在 `except: pass`、`catch {}` 等静默吞异常的代码？
- 所有 try/except 是否至少有 `logger.warning` 或用户可见的错误提示？

### 2.4 边界场景
- 列出这次改动涉及的 3-5 个关键边界 case
- 每个 case 是否有对应处理？
- 空值、异常输入、并发场景是否考虑？

### 2.5 数据模型
- 新增/修改的字段语义是否清晰？（同一个字段不应在不同场景有不同含义）
- 是否有隐式耦合？（如用字符串传 ID、魔术数字等）

### 2.6 产品化思维
- 这个改动是"临时修复"还是"长期方案"？
- 如果未来需求扩展（多一种类型、多一个数据源），现在的设计能否平滑扩展？
- 用户体验：错误情况下用户看到的是"暂无数据"还是有意义的错误提示？

## Step 3: 输出评审报告

按以下格式输出：

```
## 评审结果

### 可以提交
- [列出没有问题的文件/改动]

### 建议修改后再提交
- [问题描述] — [具体文件:行号] — [修改建议]

### 必须修改
- [严重问题] — [具体文件:行号] — [修改方案]

### 边界场景验证清单
- [ ] [场景1：描述]
- [ ] [场景2：描述]
- [ ] [场景3：描述]

### 架构建议（可选）
[如果发现当前改动暴露了更深层的架构问题，在这里指出，并给出重构方向]
```

## 重要原则

- **不要只看 diff，要结合上下文**：读取被修改文件的完整内容，理解改动在整体中的位置
- **关注"为什么改"而非"改了什么"**：如果一个 fix 是在补前一个 commit 的漏洞，要指出根因
- **给出具体的代码级建议**：不要说"建议优化"，要说"把 X 函数从 A 文件移到 B 文件，签名改为..."
- **区分严重程度**：不是所有问题都需要阻塞提交，区分"必须改"和"建议改"
