# 每日 Commit 回顾

你是一个架构师和产品专家。请对指定时间范围内的 commit 进行回顾分析。

## Step 1: 收集 Commit

```bash
# 默认查看今天的 commit，用户可指定日期范围
git log --since="today" --format="%H %s" --all
```

如果用户指定了日期或 commit 范围，按用户要求查询。

对每个 commit，获取：
- 变更文件列表：`git diff-tree --no-commit-id --name-only -r <hash>`
- 关键改动内容：`git show <hash> --stat` 和选择性查看核心文件 diff

## Step 2: 识别模式

### 2.1 补丁循环检测
- 同一个文件是否被多个 commit 连续修改？
- 后一个 commit 是否在修前一个 commit 引入的问题？（特征：fix 紧跟 feat，改同一个函数）
- 标记出"本应是一个 commit"的 commit 组

### 2.2 架构健康度
- 单个文件改动是否过于集中？（超过 3 个 commit 改同一文件 = 红灯）
- 是否存在"鸟枪式修改"？（一个逻辑变更导致 5+ 个文件改动）
- 前后端是否同步？（后端改了接口，前端是否配套？）

### 2.3 产品完成度
- 功能是否有完整的错误处理？
- 用户可见的异常场景是否有合理提示？
- 是否有遗留的 TODO / FIXME / Phase 2 注释？

## Step 3: 输出报告

```
## Commit 回顾：[日期范围]

### 概览
- 总 commit 数: X
- 有效功能 commit: X
- 跟随 fix commit: X（占比 XX%）
- 涉及文件: X

### 补丁循环（需要关注）
[列出每组"feat + follow-up fix"，说明根因和建议]

### 架构隐患
[发现的职责混杂、重复逻辑、耦合问题]

### 做得好的地方
[值得保持的实践]

### Action Items
- [ ] [具体可执行的改进项]
```

## 重要原则

- **对事不对人**：focus 在代码和流程，不评判开发者
- **给具体建议**：不说"需要重构"，说"把 X 从 A 移到 B"
- **区分紧急度**：哪些现在必须改，哪些可以排进下个迭代
